# P0 Detection API v2 contract

## Status and non-implementation notice

This is a **draft research contract**. No `/v2/detections` endpoint exists in this P0 release, and this repository does not currently calculate an AI-generation probability, model attribution, suspicious region or forensic conclusion. The existing `/v1/analyze` endpoint remains a prompt-reconstruction API and is unchanged.

The normative machine-readable response draft is [detection-result.v2.schema.json](../contracts/detection-result.v2.schema.json). The prose below explains its intended interface and invariants.

## Capability separation

| Capability | Endpoint family | Output | Never means |
| --- | --- | --- | --- |
| Prompt reconstruction | Existing `/v1/analyze` | Editable prompts and generation parameters | Source-model attribution or provenance |
| Forensic detection | Planned `/v2/detections` | `DetectionResult` | Authorship, truthfulness, or a deterministic origin verdict |
| Provenance verification | A future detector input / current internal adapter | C2PA validation observation | Proof that an asset is or is not AI-generated |

## Planned resource interface

`POST /v2/detections`

- Accepts one `image` multipart file and an optional `analysis_profile` (`screening` or `forensic`).
- Requires the same analyst authorization and upload controls as the existing protected analysis route; P0 does not alter those controls.
- Returns `202 Accepted` with `{ "detection_id", "state": "queued", "contract_version": "2.0" }` because a complete forensic assessment can require multiple detectors and an approved processing/retention policy.
- Does not accept a requested generator label, threshold, or desired verdict; caller-controlled labels would compromise evidence integrity.

`GET /v2/detections/{detection_id}`

- Returns an immutable `DetectionResult` when `state` is `complete`, or a bounded status object for `queued`, `processing`, `failed`, or `expired`.
- A future implementation must publish retention duration, access control, cancellation behaviour, audit events and error codes before enabling this route.

The API may only return `ai_probability` when `calibration.status` is `approved` and the result's model and evaluation scope are declared. Otherwise the field must be `null`, never a placeholder percentage.

## DetectionResult invariants

- `ai_probability` estimates membership in the model's defined real-versus-generated population. It is not a determination of authorship, legal provenance, intent, or authenticity.
- `confidence` describes score reliability under the declared evaluation scope. It must not be used as an independent second probability.
- `suspected_model` is an open-set hypothesis. `unknown` is always available and must be preferred to forced attribution.
- Every evidence item identifies its detector or verifier, version, evidence level and limitation. An absent EXIF record is an observation, not evidence of AI generation.
- `suspicious_regions` are localization cues for reviewer attention, not pixel-level proof. Coordinates are normalized to `[0, 1]` so they are independent of display resolution.
- C2PA and EXIF are reported in `metadata_analysis`; a valid C2PA claim only reports the verifier result under its trust policy.
- `forensic_summary` must include limitations and require human review. It may not state that an image “was generated by” a model.

## Evidence levels

| Level | Name | Meaning | Example | Prohibited interpretation |
| --- | --- | --- | --- | --- |
| `E0` | unavailable | The signal was not available, unsupported, or not run. | No readable EXIF block. | “No metadata proves AI generation.” |
| `E1` | observational | A directly observed file or image property with no detector calibration claim. | JPEG quantization table; C2PA manifest present. | “This property identifies a generator.” |
| `E2` | analytical | A deterministic or learned forensic feature that has not been approved as calibrated for this result's scope. | Frequency residual, noise consistency score, saliency map. | “This is a probability” or “this proves local tampering.” |
| `E3` | calibrated-statistical | A model score calibrated and validated on the declared population, generator time split and transformations. | Binary detection score with a linked evaluation report. | “This proves provenance” or “this generalises beyond its scope.” |
| `E4` | cryptographic-provenance | A verified cryptographic assertion evaluated under a documented trust policy. | Valid C2PA manifest with claim generator. | “No valid claim means AI-generated” or “the claim proves all image pixels are unedited.” |

Evidence levels are not a universal truth ranking: `E4` speaks to a signed provenance claim, while `E3` speaks to a statistical detector population. The response must retain both without collapsing them into a single assertion.

## Example (illustrative only)

```json
{
  "ai_probability": null,
  "confidence": {"value": null, "calibration_status": "not_evaluated"},
  "suspected_model": {"family": "unknown", "probability": null},
  "evidence": [{"level": "E1", "kind": "metadata", "finding": "EXIF absent"}],
  "suspicious_regions": [],
  "metadata_analysis": {"c2pa_status": "not_checked", "exif_status": "not_present"},
  "forensic_summary": {"review_required": true, "limitations": ["Illustrative draft; no detector ran."]}
}
```

The example deliberately has no score. It demonstrates the contract's uncertainty behaviour, not a detection result.
